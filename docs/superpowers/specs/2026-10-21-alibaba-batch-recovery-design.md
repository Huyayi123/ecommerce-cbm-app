# 物流批量同步恢复设计

## 已有证据

用户确认云端加载修复有效、单笔签收时间有效。生产批量 API 仍为 503/SYNC_PAUSED，两个 cron 的 active=false。

生产采购表约 12 MB、估算 4,097 行。物流关联表和任务表各约 32 kB，estimated_rows=-1 仅表示缺少统计信息。队列只有 (run_id,record_id) 主键索引，不能据此单独认定性能事故根因。

存在遗留 running 批次 7f9e5a3d-3707-46dc-8471-7fca49dc91e3。它不能在恢复时被直接接着执行。真实选取与领取查询计划尚待只读 EXPLAIN 核验。

## 推荐实施方案

1. 在停用状态下安装增量防护。仅为任务表补 pending/processing 部分索引，不改采购表结构。增加私有数据库控制行，分别控制手动与自动同步，初始均关闭。入口函数在选取采购数据前检查开关，恢复函数在访问队列前检查开关。
2. 核对旧批次过期且原任务仍暂停后，仅将该批次未完成任务标为 skipped，并将批次收尾、失效旧 worker token；保留成功任务、业务数据与物流摘要。不把取消旧批次说成完成了同步。
3. 每次 worker 只领取 1 笔采购记录，每笔仍最多 3 个单号，串行调用。每笔设置共享查询截止时间；worker 预算小于租约时间。查询失败保留旧成功状态和时间。
4. 为连续未被领取的派发设置最多 3 次的停止条件；成功领取才重置连续派发计数。避免暂停/失联接口使恢复任务永久重复派发。保留单活批次和一次性 token、版本/归属/提交状态校验。
5. 前端进度每 15 秒读取一次；只有完成计数增加或批次结束时才刷新摘要，隐藏页面暂停轮询。不会触发原系统全部模块重读。
6. 第一阶段最多处理 5 笔，界面明确标为试运行，不冒充“全部已刷新”。手动试运行通过后再解除数量限制，恢复权限内全部已提交记录的统一刷新。最后才恢复每 2 小时未签收同步和受限恢复任务；已签收不进入自动队列。
7. 已确认的签收解析用于试运行目标；解除单笔轨迹限制与试运行启用同步进行，仍由原独立权限控制。诊断入口不成为新的批量权限来源。

## 验证与发布顺序

先检查生产 EXPLAIN（无 ANALYZE、无实际选取），再实现与执行本地真实 SQL 回归，覆盖关闭状态零派发、旧批次收尾、一次领取、断联重试上限、并发/权限/版本冲突、时间保留与前端刷新节奏。构建通过后发布保持关闭的兼容代码。

在原项目安装增量 SQL，确认开关均关闭，再开启 5 笔手动试运行。生产观测须确认任务进度、耗时及正常页面加载不退化；若异常立即关闭数据库与 API 两侧开关。没有生产观测就不启用全量或 cron。
