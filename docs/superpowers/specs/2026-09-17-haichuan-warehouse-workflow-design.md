# 海川入仓、仓库存货与装柜审核设计

日期：2026-09-17

## 1. 目标与边界

海川物流采用“先持续送仓、再由物流商分批装柜”的模式，与现有整柜物流不同。本次设计新增一条独立的海川业务链路：

```text
我的采购订单
→ 采购订单池
→ 海川待入仓
→ 海川仓库库存
→ 海川提交装柜批次
→ 我方审核
→ 采购／海运在途库存
```

本次必须遵守以下边界：

- 整柜现有生成批次、物流确认和审核流程保持不变。
- 冠通现有直接进入采购／在途库存的规则保持不变。
- 海川修改的是物流包装件数，不得修改我方采购的产品总数量、采购单价或采购总金额。
- 相同 SKU 的不同采购记录不合并，保留采购人、供应商、采购批次和入仓批次来源。
- 所有数量变化必须可追踪、可重试且不能重复生效。

## 2. 统一术语

为避免现有界面中“件数”和“数量”混用，本流程统一定义：

- **件数／箱数**：物流包装箱的数量。
- **每箱数量**：一个标准整箱内包含的产品个数。
- **产品数量／采购总数量**：实际购买的商品个数。
- **尾箱数量**：不足一个标准整箱时，尾箱内的产品个数。
- **单品 CBM**：单个产品的体积。
- **总 CBM**：我方传入的该采购记录总体积。

我方原始包装关系为：

```text
采购总数量 = 整箱件数 × 每箱数量 + 尾箱数量
申报总件数 = 整箱件数 +（尾箱数量 > 0 ? 1 : 0）
```

## 3. 我的采购订单提交规则

点击“提交采购订单池”时，只提交同时满足以下条件的待采购记录：

- 实际采购数量大于 0。
- 总金额大于 0。

未满足条件的记录继续保留在“我的采购订单”，不得因为同批其他记录满足条件而一起提交。

提交前必须先提交当前页面尚未失焦的编辑草稿，避免用户刚输入数值便点击按钮时读取到旧数据。操作完成后提示：

- 成功提交多少条。
- 因实际数量为空或为 0 跳过多少条。
- 因总金额为空或为 0 跳过多少条。
- 保存失败的记录及失败原因。

## 4. 物流商账号绑定

`profiles` 增加物流商类型，仅对 `role = logistics` 的账号生效：

- `container`：整柜物流商。
- `haichuan`：海川物流商。

管理员在账号绑定区域完成一次绑定。装货方式为“海川”的采购池记录自动分配给已启用的海川物流账号，不再由管理员每批手动选择物流商。

如果没有绑定海川账号，记录保留在采购池并明确提示“未绑定海川物流商”，不得静默丢失或误发给整柜物流商。

## 5. 海川待入仓

### 5.1 展示字段

海川物流的“待入仓”页面显示：

- 产品名称。
- 内部编号。
- SKU。
- 采购总数量，只读。
- 我方申报总件数，只读。
- 我方申报每箱数量，只读，仅供参考。
- 我方申报尾箱数量，只读。
- 海川实际收到总件数，默认等于我方申报总件数，海川可修改。
- 单品 CBM，只读。
- 我方传入的总 CBM，只读。
- 当前处理状态。

海川只确认实际收到的总件数。海川无法核对每箱产品数量，因此不得要求其填写或修改每箱数量，也不得让其修改采购总数量。

### 5.2 入仓确认规则

- 实际收到总件数必须为大于 0 的整数。
- 允许小于、等于或大于我方申报总件数。
- 海川一次确认后，以填写的件数作为最终入仓件数。
- 即使实际件数少于申报件数，也不保留差额继续待入仓。
- 系统保留申报件数、实际件数、差异值、确认人和确认时间。
- 入仓确认不需要我方再次审核。
- 确认成功后，采购池中的该条记录退出采购池，并进入海川仓库库存。
- 我方传入的总 CBM 在待入仓阶段原样展示，不因实际箱数变化而改写。

### 5.3 包装差异标记

当实际收到总件数等于申报总件数时，沿用我方原有整箱数、每箱数量和尾箱数量，后续装柜数量可以精确计算。

当实际收到总件数不等于申报总件数时：

- 标记为“包装件数有差异”。
- 采购总数量保持不变。
- 总 CBM 保持我方传入值。
- 不猜测或改写每箱数量。
- 只有后续发生部分装柜时，才按箱数比例生成“系统估算数量”。

## 6. 海川仓库库存

我方新增页面“海川仓库库存”，海川物流端新增“仓库存货”。两边读取同一库存批次，但权限不同。

每次入仓确认创建一个独立库存批次，保存：

- 原采购记录和入仓任务标识。
- 产品、采购人、供应商和采购批次快照。
- 入仓总件数、剩余件数、冻结件数。
- 采购总数量、剩余产品数量。
- 入仓总 CBM、剩余 CBM。
- 原申报包装信息。
- 是否存在包装件数差异。
- 入仓确认人、确认时间及版本号。

相同 SKU 不自动合并。页面支持按 SKU、产品名称、内部编号搜索，可在顶部提供汇总数字，但汇总不能替代明细批次。

库存可用件数计算为：

```text
可用件数 = 剩余件数 - 冻结件数
```

数量为零的库存批次从默认可装柜列表隐藏，但保留在历史查询中。

### 6.1 表头一致性

采购相关页面表格较多，同一业务字段必须使用统一的中文表头、字段含义和基础顺序。海川待入仓、海川仓库存货、海川装柜审核、采购订单池和采购／在途库存中出现相同字段时，不允许另起近义名称。

统一表头定义：

| 数据字段 | 统一表头 | 含义 |
| --- | --- | --- |
| `productName` | 产品名称 | 商品中文名称 |
| `internalCode` | 内部编号 | 系统内部商品编号 |
| `sku` | SKU | 商品 SKU |
| `purchaseTotalQuantity` / 对应采购数量字段 | 采购总数量 | 实际购买的产品个数，不是箱数 |
| `cartonCount` | 整箱件数 | 标准整箱的箱数 |
| `unitsPerCarton` | 每箱数量 | 一个标准整箱内的产品个数 |
| `tailQuantity` | 尾箱数量 | 尾箱内的产品个数，不是尾箱箱数 |
| 计算字段 | 总件数 | 整箱件数加尾箱是否存在，表示总箱数 |
| `unitCbm` | 单品 CBM | 单个产品体积 |
| `totalCbm` | 总 CBM | 当前记录总体积 |
| `loadingType` | 装货方式 | 整柜、冠通或海川 |
| `containerDate` | 装柜日期 | 最终使用的装柜日期 |
| 状态字段 | 状态 | 当前业务状态 |
| `note` | 备注 | 业务备注或退回说明 |

其中“尾箱数量”固定表示尾箱内的产品数量。若尾箱数量大于 0，则总件数增加 1；不得把“尾箱数量”显示成“尾箱件数”或把它理解成多个尾箱。

实现时应建立共享表头常量和可复用的采购商品列配置。各页面可以按业务需要隐藏无关列，但只要显示同一字段，就必须使用上述统一名称，不在各页面分别硬编码不同文案。

## 7. 海川创建装柜批次

海川从“仓库存货”选择一个或多个库存批次，填写装柜日期并生成一个装柜批次。

- 每条记录默认装走全部可用件数。
- 海川可以减少本次装柜件数。
- 本次装柜件数必须为整数，并且不能超过可用件数。
- 同一产品有 10 箱时，可以本次装 6 箱，剩余 4 箱留待下次装柜。
- 提交审核后立即冻结本次件数，审核结束前不能再次选择，防止重复装柜。

### 7.1 无包装差异时的精确计算

当入仓实际件数等于我方申报件数时，按原包装信息计算装柜产品数量：

```text
装柜产品数量 = 装柜整箱件数 × 每箱数量 + 本次尾箱数量
装柜总 CBM = 装柜产品数量 × 单品 CBM
```

系统默认优先装走标准整箱，尾箱作为最后一箱处理；选择全部剩余件数时，必须同时带走全部剩余产品数量。

### 7.2 有包装差异时的估算

只有入仓实际件数与申报件数不一致，并且本次不是全部装走时，才使用比例估算：

```text
估算装柜产品数量
= 当前剩余产品数量 × 本次装柜件数 ÷ 当前剩余件数

估算装柜 CBM
= 当前剩余 CBM × 本次装柜件数 ÷ 当前剩余件数
```

- 非最后一批的产品数量按统一规则取整，并标记“系统估算数量”。
- 最后一次装走全部剩余件数时，直接带走全部剩余产品数量和剩余 CBM，消除累计取整误差。
- 海川只选择件数，不负责确认估算出来的箱内产品数量。

## 8. 我方装柜审核

现有“物流装柜确认”页面按流程区分“整柜审核”和“海川审核”。整柜审核保持原逻辑；海川审核展示海川提交的批次和库存来源。

我方可以修改：

- 最终确认的装柜件数。
- 最终确认的装柜产品数量。
- 装柜日期。
- 审核备注或退回原因。

我方有两种处理方式：

### 8.1 确认

- 以我方最终确认件数和产品数量为准。
- 校验最终件数不超过该库存批次的“当前可用件数 + 本批已冻结件数”。
- 校验最终产品数量不超过该库存批次的剩余产品数量。
- 原子扣减剩余件数、剩余产品数量和剩余 CBM。
- 解除本批冻结件数。
- 为确认装走的部分生成新的采购／海运在途记录，并通过来源字段关联原采购记录、仓库批次和装柜批次。
- 海川端对应批次进入“已装柜”。
- 剩余部分继续保留在海川仓库库存。

### 8.2 退回

- 不扣减仓库库存。
- 解除本批冻结件数。
- 保存我方修改后的建议值和退回原因。
- 海川可以查看后修改并重新提交。

## 9. 海川物流端页面

海川物流账号只看到三个业务页签：

1. **待入仓**：我方已提交采购池、正在送往海川仓库的记录。
2. **仓库存货**：已经确认入仓且仍有剩余件数的库存批次。
3. **已装柜**：我方审核通过的装柜批次和明细。

物流商只能访问分配给自己账号的数据，不能读取全部 `purchase_records`、其他物流商批次、采购价格或采购金额。

## 10. 状态与交互反馈

建议状态如下：

### 入仓任务

- `pending_receipt`：待入仓。
- `receiving`：正在确认，仅用于前端短暂状态。
- `received`：已入仓。

### 仓库批次

- `available`：有可用库存。
- `partially_reserved`：部分数量正在审核。
- `fully_reserved`：全部剩余数量正在审核。
- `depleted`：已经全部装走。

### 装柜批次

- `draft`：编辑中。
- `submitting`：正在提交，仅用于前端短暂状态。
- `submitted`：审核中。
- `rejected`：已退回。
- `approving`：正在确认，仅用于前端短暂状态。
- `approved`：已确认／已装柜。

所有关键按钮必须：

- 请求进行中时禁用并显示“正在提交”或“正在确认”。
- 成功后明确提示并刷新状态。
- 失败时显示可理解的失败原因并允许重试。
- 不采用乐观扣减库存；数据库成功后才更新本地最终状态。

## 11. 推荐数据模型

为保证整柜流程不受影响，不把海川入仓和仓库状态硬塞进现有 `logistics_batches`。采用独立表，并通过来源 ID 与采购记录关联。

### 11.1 `profiles` 扩展

新增：

- `logistics_provider_type text null`，允许值 `container`、`haichuan`。

### 11.2 `haichuan_inbound_items`

记录发往海川及入仓确认快照，主要字段：

- `id`。
- `purchase_record_id`，唯一约束防止重复派发。
- `logistics_user_id`、`logistics_email`。
- 产品名称、内部编号、SKU 等必要只读快照。
- `purchase_total_quantity`。
- `declared_carton_count`、`declared_units_per_carton`、`declared_tail_quantity`。
- `actual_received_carton_count`。
- `unit_cbm`、`declared_total_cbm`。
- `has_packing_variance`。
- `status`、`received_by`、`received_at`。
- `created_at`、`updated_at`。

### 11.3 `haichuan_warehouse_lots`

一条已入仓任务对应一个库存批次，主要字段：

- `id`、`inbound_item_id`、`purchase_record_id`。
- `initial_carton_count`、`remaining_carton_count`、`reserved_carton_count`。
- `initial_product_quantity`、`remaining_product_quantity`。
- `initial_cbm`、`remaining_cbm`。
- 原包装快照和 `has_packing_variance`。
- `status`、`version`。
- `created_at`、`updated_at`。

### 11.4 `haichuan_loading_batches`

保存一次多产品装柜申请：

- `id`、`container_date`。
- `logistics_user_id`、`logistics_email`。
- `status`。
- `created_by`、`submitted_at`、`reviewed_by`、`reviewed_at`。
- `note`、`rejection_reason`。
- `created_at`、`updated_at`。

### 11.5 `haichuan_loading_items`

- `id`、`batch_id`、`warehouse_lot_id`。
- `requested_carton_count`。
- `suggested_product_quantity`、`suggested_cbm`。
- `is_estimated`。
- `approved_carton_count`、`approved_product_quantity`、`approved_cbm`。
- 提交时的库存版本和必要产品快照。
- `created_at`、`updated_at`。

### 11.6 采购记录状态

`PurchaseRecordPoolStatus` 增加 `haichuan_warehouse`：

- 发往海川、尚未入仓时仍为 `submitted_to_pool`，采购池可显示运输状态但不能重复派发。
- 入仓确认后改为 `haichuan_warehouse`，从采购池移出，也不会提前进入采购／海运在途库存。
- 我方审核装柜通过后，为装走部分创建 `sent_to_inventory` 的来源拆分记录。

## 12. 数据库事务与重复操作保护

关键操作不能由前端连续执行多个普通 upsert 完成，应使用 Supabase/PostgreSQL RPC 或数据库函数在单事务内完成。

### 12.1 确认入仓事务

事务内完成：

1. 锁定入仓任务并校验状态为 `pending_receipt`。
2. 将任务改为 `received`。
3. 使用 `inbound_item_id` 唯一约束创建仓库批次。
4. 将采购记录改为 `haichuan_warehouse`。

重复请求返回已经完成的结果，不重复创建库存。

### 12.2 提交装柜事务

事务内完成：

1. 锁定相关仓库批次。
2. 重新计算可用件数。
3. 校验本次件数不超库存。
4. 创建或更新装柜批次与明细。
5. 增加冻结件数并将批次改为 `submitted`。

每个仓库批次使用 `version` 或条件更新防止两个页面同时提交造成超卖。

### 12.3 审核确认事务

事务内完成：

1. 锁定装柜批次和仓库批次。
2. 校验批次仍为 `submitted`。
3. 校验最终件数和产品数量。
4. 扣减剩余量并解除冻结量。
5. 创建海运在途拆分记录。
6. 将批次改为 `approved`。

拆分记录以装柜明细 ID 建唯一约束，确保重复审核不会重复进入在途库存。

### 12.4 审核退回事务

事务内解除冻结量、保存我方修改值和退回原因，并将批次改为 `rejected`。重复退回不能重复减少冻结量。

## 13. RLS 权限策略

- 管理员／所有者可读写所有海川业务表。
- 海川物流账号只能读取分配给自己的入仓任务、库存批次和装柜批次。
- 海川物流只能确认自己的待入仓任务，或编辑自己 `draft/rejected` 状态的装柜批次。
- `submitted/approved` 状态的装柜数据禁止物流商继续修改。
- 海川物流不直接获得 `purchase_records` 的读取权限，避免采购金额等字段泄露。
- 需要展示的商品与包装字段通过海川专用表的只读快照提供。

## 14. 实施顺序

### 阶段一：数据库与兼容层

1. 为 `profiles` 增加物流商类型。
2. 新建四张海川业务表、索引、唯一约束和 RLS。
3. 新建确认入仓、提交装柜、审核确认、审核退回 RPC。
4. 扩展采购记录池状态，但保留旧状态的读取兼容。
5. 先执行只读迁移预检，统计已有海川记录和旧批次，确认不会重复生成任务后再回填。

### 阶段二：类型与数据访问

1. 在 `src/types.ts` 增加物流商类型、海川入仓、库存和装柜类型。
2. 在 `src/utils/cloudStorage.ts` 增加映射、查询、订阅和 RPC 调用。
3. 新建纯函数模块，集中实现精确计算、差异估算、最后一批余量归集和状态显示。
4. 建立共享采购表头常量和公共列定义，统一产品名称、内部编号、SKU、采购总数量、整箱件数、每箱数量、尾箱数量、总件数、单品 CBM、总 CBM 等名称。
5. 保持现有 `src/utils/logistics.ts` 的整柜逻辑不变。

### 阶段三：采购提交与自动派发

## 15. 核心验收用例

### 采购提交

- 实际数量和总金额都有值：成功提交。
- 任一字段为空或为 0：不提交，仍留在我的采购订单。
- 多条混合提交：仅合格记录进入采购池，提示提交和跳过数量。

### 入仓

- 实际件数等于申报件数：不标记估算，沿用原包装。
- 实际件数小于申报件数：一次完成入仓，不保留差额待入仓。
- 实际件数大于申报件数：允许入仓，采购总数量和金额不变。
- 待入仓页面显示申报尾箱数量，且海川不能修改。
- 重复点击确认：只产生一个仓库批次。

### 装柜

- 10 箱默认装 10 箱。
- 10 箱改为装 6 箱：冻结 6 箱，剩余 4 箱仍在仓库。
- 审核中再次选择同一批冻结数量：不能重复选择。
- 无包装差异：按原每箱数量精确计算产品数量和 CBM。
- 有包装差异：部分装柜按比例估算并显示标记。
- 有包装差异且最后全部装走：带走全部剩余产品数量和 CBM。

### 审核

- 我方修改数量后确认：按最终值扣库并进入在途。
- 我方退回：库存不扣减，冻结释放，海川可重新提交。
- 重复点击审核确认：只生成一条在途拆分记录。
- 并发审核或库存变化：事务拒绝过量扣减，库存永不为负。

### 回归

- 整柜批次的生成、提交、审核和剩余退回逻辑结果不变。
- 冠通送入采购／在途库存的逻辑结果不变。
- 我的采购订单单条保存、日期保存和采购池退回单条逻辑不变。
- 采购／在途库存筛选、导出和已到货操作不变。
- 同一字段在采购池、待入仓、仓库存货、装柜审核和在途库存中的表头名称一致。
- “尾箱数量”始终表示尾箱内产品个数，“总件数”始终表示总箱数。
- `npm.cmd run build` 通过。

## 16. 风险控制

- 数据库变更全部采用新增字段／新增表，不删除现有物流表或字段。
- 新海川服务函数与现有整柜 `logistics.ts` 分离，减少回归范围。
- 数据迁移先输出预览数量，再执行幂等回填。
- 库存增减只在数据库事务内完成，前端不直接计算并覆盖最终库存。
- 所有拆分记录保留 `purchase_record_id`、`warehouse_lot_id` 和 `loading_item_id` 来源链路。
- 已确认数据不提供直接删除；后续如需纠错，增加有审计记录的库存调整流程。
