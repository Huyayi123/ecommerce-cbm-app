# Not Buyable 历史销量回退与最低采购量设计

## 目标

避免 Takealot 产品因缺货进入 `Not Buyable` 后当前销量变为 0，导致系统长期不生成采购建议。

手动同步“月销量采购建议”和每周一自动扫描统一使用前两个完整自然月的历史销量回退规则，并更新建议采购数量的最低值规则。

## 状态识别

从 Takealot 商品数据的以下字段识别状态：

- `status`
- `offer_status`
- `buyability`
- `buyable`
- `is_buyable`
- `isBuyable`

处理规则：

- 明确包含 `Not Buyable`、`not_buyable` 或 `not-buyable`：执行历史销量回退。
- 明确为 `disabled`：继续过滤，不进入采购建议或装柜计算。
- 明确为 `Buyable`：继续使用当前 `sales_units`。
- 无法识别：继续使用当前 `sales_units`，不使用历史回退。

匹配时忽略大小写，并允许 `Not Buyable` 中间使用空格、下划线或连字符。

## 历史销量范围

`Not Buyable` 产品查询同步日期之前的两个完整自然月，不包含当前月。

例如，2026 年 10 月任意一天同步时：

```text
第一个月份：2026-08-01 至 2026-08-31
第二个月份：2026-09-01 至 2026-09-30
```

日期边界按北京时间确定。

## 历史销量计算

1. 每个店铺一次性查询完整两个月范围的 Takealot Sales API。
2. 处理全部分页或 continuation token，不能只使用第一页。
3. 按“店铺 + 规范化 SKU + 自然月”汇总有效销售数量。
4. 将 `sale_status` 转为小写后，包含 `cancel`、`refund`、`return` 或 `failed` 的记录不计入销量；其他 SKU、日期和正数数量均有效的销售记录计入销量。
5. 分别得到两个自然月的销量，取较高值作为该 `Not Buyable` 产品的预测月销量。
6. 两个月销量均为 0 时，预测月销量保持 0，不生成采购建议。

示例：

```text
8 月销量：35
9 月销量：52
最终预测月销量：52
```

页面备注显示历史取值依据，例如：

```text
Not Buyable：8月销量35，9月销量52，取最高值52
```

## 与新品预测的关系

- `Not Buyable` 产品使用历史最高月销量后，不再叠加 Bestby、Aicom 或 Arfast 的新品倍率或新品固定目标数量。
- `Buyable` 和状态未知产品继续使用现有新品预测规则。
- `disabled` 产品已过滤，不参与新品排序或采购计算。

## 建议采购数量

先使用预测月销量执行现有备货月数与库存扣减：

```text
原始建议采购数量
= 预测月销量 × 备货月数
- 南非本地库存
- Takealot 官方仓库存
- 送仓路上库存
- 海运在途库存
```

随后应用新的最低采购量规则：

- 预测月销量大于或等于 10，原始建议数量大于 0 且小于 50：最终建议数量为 50。
- 预测月销量大于或等于 5 且小于 10，原始建议数量大于 0 且小于 30：最终建议数量为 30。
- 原始建议数量等于 0：继续为 0，不强制采购。
- 其他情况保持原始建议数量。

该规则替换现有“月销量大于 5 且建议数量不足 30 时补到 30”的规则。

## 架构与复用

建立共享的服务端历史销量与状态计算模块，供以下入口共同使用：

- `api/takealot-inventory.js` 的手动店铺同步；
- `api/cron/takealot-weekly-sync.js` 的每周自动扫描。

共享模块负责：

- 商品状态识别；
- 前两个完整自然月日期范围；
- Takealot Sales API 分页；
- 无效销售过滤；
- 按 SKU 和月份汇总；
- Not Buyable 历史最高销量及说明文本。

手动同步接口返回状态、历史两月销量和最终采用的基础月销量，使前端使用后端结果，避免前端与定时任务重复实现或出现不同口径。

## 使用范围

规则同时用于：

1. 用户在“月销量采购建议”页面手动同步店铺；
2. 每周一北京时间上午 9:00 自动扫描 Bestby、Aicom、Arfast，并覆盖装柜计算。

现有装柜计算及后续采购任务流程保持不变。

## 错误处理

- Sales API 历史销量请求失败时，该店铺同步失败，不用 0 代替历史销量。
- 手动同步失败时显示错误，并保留页面已有数据。
- 每周自动扫描任一店铺失败时，不覆盖现有装柜计算。
- 单条销售记录缺少 SKU、日期无效、数量不是正数，或状态命中 `cancel`、`refund`、`return`、`failed` 时忽略该记录，并纳入诊断计数。

## 验证

至少覆盖以下场景：

1. `Not Buyable` 的空格、下划线、连字符及大小写变体均能识别。
2. `disabled` 产品继续被过滤。
3. Buyable 与未知状态产品保持当前销量逻辑。
4. 10 月同步时准确查询并汇总 8 月和 9 月。
5. Sales API 多页数据全部计入。
6. 取消、退款和无效记录不计入销量。
7. 两个月分别有销量时取最高值。
8. 两个月销量均为 0 时最终月销量为 0。
9. Not Buyable 新品不叠加新品倍率或固定目标数量。
10. 月销量 5、9、10 的最低采购量边界正确。
11. 原始建议数量为 0 时不强制补到 30 或 50。
12. 月销量大于或等于 10、建议数量 1–49 时调整为 50。
13. 月销量 5–9、建议数量 1–29 时调整为 30。
14. 手动同步和每周自动扫描得到相同结果。
15. 历史销量请求失败时不覆盖原有页面数据或装柜数据。
