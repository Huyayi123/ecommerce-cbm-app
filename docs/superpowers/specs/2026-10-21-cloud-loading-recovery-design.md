# 云端加载恢复方案

## 已确认事实

- 用户已在生产 SQL Editor 确认两个 Alibaba cron 均为 active=false；正式批量 API 返回 SYNC_PAUSED。
- 一次数据库活动快照未显示业务阻塞；不能据此排除间歇性数据库负载。
- 用户网络截图中的采购读取多次返回 200，单次约 0.6–2.5 秒；未提供完整瀑布图，不能精确计算总耗时。
- 当前采购读取使用主键游标，每次 200 条串行读取，全部成功才交付；保持这个大小及页面展示分页不变。
- App 同时通过 loadSession 和 onAuthStateChange 发起首次加载；当前合并器默认排一次后续完整加载。回调未区分 INITIAL_SESSION、TOKEN_REFRESHED 和 SIGNED_IN。
- App 在所有模块完成后才更新数据，loadSession 又等待全部加载才设置 authReady。这一等待逻辑在当前 Git 基线中已存在。
- 新增物流摘要不在全局实时订阅列表中；截图中四类物流读取约 0.3 秒。不能据此认定物流功能完全无性能影响。

## 建议实施范围

1. 启动加载复用同一用户正在执行的加载，不排第二轮；忽略不需要刷新业务数据的初始会话及 Token 刷新事件，保留真实业务操作和实时数据变更的后续刷新。
2. 身份与权限读取成功后展示应用壳；各模块完整读取成功即可独立更新。采购记录仍须完整读取成功后交付，失败不展示半份记录。
3. 保留采购与采购池、海川补建的依赖和原业务操作；依赖齐备后再进行关联处理，不因提前展示模块而提前写入。
4. 批量同步继续关闭，不变更数据库、物流规则、采购分页大小及界面分页。

## 验证与边界

- 模拟 INITIAL_SESSION、SIGNED_IN、TOKEN_REFRESHED 与会话初始化重叠，验证相同用户只有一轮启动读取；真实实时事件仍可安排一次后续读取。
- 模拟慢模块和采购分页失败，验证独立模块可展示、采购不会交付半份数据、错误可见；登录期间不会泄漏旧用户数据。
- 运行采购加载回归、Alibaba 回归及生产构建。
- 本地测试不等于生产性能恢复。部署后需通过一次实际加载观察请求轮数和页面可用时间；最初性能事故根因仍未确认。
