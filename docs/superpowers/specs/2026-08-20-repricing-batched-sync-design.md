# 价格预警分批同步设计

## 问题

Bestby 有一千余条有效 offers。现有 `/api/repricing-monitor` 在一次 Vercel 请求中逐条读取商品详情并保存，超过函数执行时限后返回 504，导致本轮检测无法完整结束。

## 服务端设计

- 新增 `offset`、`batchSize` 和 `reset` 查询参数。
- 每个批次仍读取完整 offers 作为变体判断上下文，但只检测当前切片内的商品。
- `reset=1` 仅用于第一批，先清理该店铺旧的有效预警；后续批次累积写入，不重复清理。
- 每批以受控并发处理商品详情及 Supabase 写入，缩短单批耗时且避免过高并发。
- 响应增加 `totalRows`、`offset`、`nextOffset` 和 `hasMore`，并继续返回本批 `alertDetails`。
- 未提供分批参数时保留现有单次调用兼容行为。

## 前端设计

- “同步店铺”改为循环调用分批接口。
- 第一批传 `reset=1`，后续批次使用 `nextOffset`，直到 `hasMore=false`。
- 页面持续显示批次进度，全部完成后刷新 Supabase 数据并展示合计检查数、确认预警数和跳过原因。
- 任一批失败时停止后续请求并明确提示已完成进度，避免显示为完整结果。

## 导出任务

- 部署后使用相同分批接口完整检查 Bestby，并汇总每批 `alertDetails`。
- Excel 包含 SKU、产品名称、我方售价、Buy Box、竞争卖家、竞品价、差价、预警类型、数据来源、说明和检测时间。
- 生成后检查关键范围、公式错误和页面渲染，最终只交付完整结果表格。

## 验证

- 验证第一批清理一次、后续批次不清理、offset 连续且无重复/遗漏。
- 验证多批统计合计与最终有效预警数量一致。
- 验证单批失败不会宣称同步完成。
- 运行 TypeScript/Vite 构建，并用公网 Bestby 全量同步验证无 504。
