# 海川多账号共享数据与操作权限设计

## 背景

系统允许多个账号设置为“海川物流商”，但现有海川业务数据通过 `logistics_user_id` 和 `logistics_email` 绑定到单个登录账号。数据库行级安全策略和业务函数也按这个账号归属判断权限。因此，新注册的海川账号虽然能进入海川物流工作台，却看不到旧账号名下的待入仓、仓库存货和已装柜数据，也不能参与同一批业务操作。

当前业务只有一个海川物流机构。两个及以后新增的海川物流账号应作为同一机构的操作成员，共享全部海川数据和操作权限。

## 目标

- 所有角色为 `logistics` 且 `logistics_provider_type = 'haichuan'` 的账号，均可查看全部海川待入仓、仓库存货、装柜批次和已装柜明细。
- 所有海川物流账号均可确认入仓、选择库存并提交装柜审核，以及修改并重新提交被退回的装柜批次。
- 历史数据立即对新海川账号可见，无须复制记录或逐条改绑。
- 保留实际操作账号信息，便于追踪是谁创建或提交了装柜批次。
- 普通整柜物流账号和未绑定物流类型的账号不能访问海川数据。
- 管理员和所有者维持现有海川管理权限。

## 非目标

- 本次不支持多家彼此隔离的“海川型”仓库机构。
- 不新增物流机构管理页面或机构表。
- 不复制海川业务记录，也不把同一条记录分别绑定到多个账号。
- 不改变管理员审核、库存扣减或海运在途生成的业务规则。
- 不改变普通整柜物流商的数据权限。

## 方案选择

采用“海川类型即机构成员身份”的共享方案。数据库根据当前登录用户在 `profiles` 中的角色和 `logistics_provider_type` 判断其是否属于海川，而不是根据业务记录上的账号 ID 或邮箱决定访问权。

未采用独立 `logistics_provider_id` 的原因是当前只有一家海川机构，引入机构表、成员关系和管理界面会增加不必要的迁移与维护成本。如果未来需要接入多家同类型且必须相互隔离的仓库，应另行升级为机构 ID 模型。

## 权限架构

### 海川成员判断

新增稳定的数据库辅助函数，例如 `public.is_haichuan_logistics()`。函数依据 `auth.uid()` 查询当前用户自己的 `profiles` 记录，并仅在以下条件同时满足时返回真：

- `role = 'logistics'`
- `logistics_provider_type = 'haichuan'`

函数应使用与现有 `current_role()`、`is_admin()` 一致的安全模式和固定 `search_path`，避免调用者自行伪造身份或读取其他账号资料。

### 行级安全策略

下列海川业务表的读取策略调整为：管理员或所有者可以读取；海川物流成员可以读取全部记录。

- `haichuan_inbound_items`
- `haichuan_warehouse_lots`
- `haichuan_loading_batches`
- `haichuan_loading_items`，通过所属批次判断

不再以记录上的 `logistics_user_id = auth.uid()` 或 `logistics_email = JWT email` 作为海川成员读取数据的必要条件。字段继续保留，用于历史来源和审计兼容。

### 业务函数授权

确认入仓和提交装柜等现有数据库函数中，原来允许“管理员或记录所属账号”操作的判断改为“管理员或海川物流成员”。函数内部现有的记录状态、库存余量、冻结数量和批次状态校验继续生效。

管理员专属操作保持不变，包括审核装柜、修改仓库采购总数量和删除仓库记录。

## 数据流与审计

采购侧创建待入仓任务时，仍可写入一个海川账号的 `logistics_user_id` 和 `logistics_email`，以兼容现有表结构和历史数据。该绑定不再控制海川成员之间的访问权限。

海川账号创建装柜批次时：

- `created_by` 记录真实操作账号的用户 ID。
- 批次现有的物流账号字段可继续记录创建者，作为审计信息。
- 其他海川账号仍可查看、修改草稿或退回批次并重新提交。

本次不需要重写历史记录。数据库策略部署后，旧账号名下的全部历史数据会立即对新海川账号可见。

## 并发与错误处理

两个海川账号可能同时操作同一条待入仓记录或同一个库存批次。数据库函数必须继续在事务内锁定并重新读取目标记录，验证当前状态和可用库存后再写入。

- 同一待入仓记录只允许从 `pending_receipt` 成功确认一次。
- 同一库存数量不能被两个装柜提交重复冻结。
- 已被其他账号处理的记录，后提交者收到明确的状态变化或库存不足错误，并刷新页面获取最新数据。
- 前端不通过本地隐藏或过滤代替数据库权限控制。

## 前端行为

海川物流工作台布局不变。新账号登录或点击刷新后，应看到与旧账号一致的：

- 待入仓记录
- 仓库存货
- 已装柜产品
- 被退回、允许修改后重新提交的装柜批次

前端继续调用统一的 `fetchHaichuanData()`，不按当前账号再次过滤数据。是否可见和可操作由数据库权限与业务函数统一决定。

管理员“物流商绑定”页面保持现状。把账号保存为“海川物流商”后，该账号下一次重新加载身份或重新登录即可获得海川机构共享权限；解绑后立即失去权限。

## 数据库迁移与发布

创建独立、可重复执行的 SQL 迁移，并同步更新根目录的 `supabase.sql` 基线定义。迁移顺序如下：

1. 创建或替换海川成员判断函数。
2. 替换四张海川业务表的相关行级安全策略。
3. 更新确认入仓、提交装柜等海川业务函数的授权条件。
4. 保留原字段和历史数据，不执行批量复制或账号改绑。

若只发布前端而未部署数据库迁移，新账号仍看不到数据。因此数据库迁移是本功能生效的必要发布步骤。

## 验证方案

### 权限验证

- 旧海川账号能读取全部历史和新增海川数据。
- 新海川账号读取结果与旧账号一致。
- 任一海川账号创建或处理的数据可被另一海川账号立即看到。
- 普通整柜物流账号、未绑定物流账号无法读取海川业务表。
- 管理员和所有者维持完整读取和管理能力。

### 流程验证

- 新账号成功确认旧账号名下的待入仓记录，两个账号刷新后均看到库存结果。
- 新账号从共享库存提交装柜审核，旧账号能查看该批次。
- 管理员退回后，任一海川账号均可修改并重新提交。
- 管理员审核通过后，两个账号都能在“已装柜”看到相同产品明细。

### 并发验证

- 两个账号同时确认同一待入仓记录，只有一次成功，不产生重复仓库库存。
- 两个账号同时使用同一库存提交装柜时，冻结数量不能超过可用数量。
- 操作冲突后，失败账号刷新即可看到最终一致状态。

## 验收标准

- 两个海川物流账号登录后看到相同的待入仓、仓库存货和已装柜数据。
- 两个账号都能完成海川物流端现有的全部操作。
- 所有关键写操作仍保持幂等和库存一致性。
- 非海川物流账号无法读取或操作海川数据。
- 不需要迁移、复制或重新归属历史海川业务记录。
