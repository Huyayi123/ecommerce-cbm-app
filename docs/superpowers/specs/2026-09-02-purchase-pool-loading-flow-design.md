# 采购订单池整柜与冠通分流设计

## 背景

采购订单池同时包含“整柜”和“冠通”两种装货方式。整柜需要物流商确认实际装柜情况，冠通不需要物流商参与，应由管理员填写装柜日期后直接进入采购 / 在途库存。当前系统会把冠通包含在统一日期和物流批次流程中，也缺少冠通直接进入在途库存的入口。

## 目标

- 整柜继续经过物流确认和管理员审核。
- 冠通跳过物流模块，填写装柜日期后由管理员批量发送到采购 / 在途库存。
- 统一本池装柜日期只影响整柜记录。
- 整柜记录若已逐行修改为不同日期，统一日期时保留该人工日期。
- 采购池中继续允许管理员修改每条记录的装货方式。
- “退回采购人”继续保持单条操作，按钮文字不变。

## 业务流程

```text
整柜：
采购订单池 → 物流商确认 → 管理员审核 → 采购 / 在途库存

冠通：
采购订单池 → 管理员逐行填写装柜日期
→ 发送已填日期的冠通到在途库存 → 采购 / 在途库存
```

## 详细设计

### 1. 退回采购人

“退回采购人”继续按采购记录 ID 处理当前行：

- 从当前采购池移除点击的单条记录。
- 将该记录恢复为采购人的待采购记录。
- 不处理同一采购人的其他产品。
- 按钮文字保持“退回采购人”。

### 2. 采购人提交到采购池

采购记录提交到采购池时按装货方式处理日期：

- 整柜：保留现有池日期逻辑。
- 冠通：`containerDate` 默认为空，不继承采购池的统一装柜日期。

采购池自身的日期仍可作为整柜的计划装柜日期；冠通日期由管理员后续逐行填写。

### 3. 统一本池装柜日期

点击“统一本池装柜日期”时：

- 只考虑当前池中装货方式不是“冠通”的记录；空装货方式按“整柜”处理。
- 整柜记录的日期为空，或日期仍等于本池修改前的统一日期时，更新为新日期。
- 整柜记录的日期已被逐行修改为其他日期时，视为人工日期并保持不变。
- 更新整柜记录的 `containerDate` 以及现有批次日期兼容字段。
- 冠通记录的日期及其他字段完全保持不变。
- 提示信息分别说明更新了多少条整柜记录、保留了多少条人工日期、跳过了多少条冠通记录。
- 如果池内没有整柜记录，不写入采购记录，只显示明确提示。

### 4. 修改装货方式

管理员继续可以在采购池表格中把装货方式修改为“整柜”或“冠通”，失焦后保存。

- 整柜改为冠通：保存装货方式并清空 `containerDate`，避免沿用整柜日期。
- 冠通改为整柜：保存装货方式，日期保持空；管理员可随后使用统一日期按钮或逐行填写。
- 修改采购池内嵌记录和采购记录主表时使用同一份规范化记录，避免刷新后回滚。

### 5. 冠通直接发送到采购 / 在途库存

采购池顶部新增管理员按钮：

```text
发送已填日期的冠通到在途库存
```

点击一次处理当前池内全部满足以下条件的记录：

- `poolStatus` 为 `submitted_to_pool`。
- 状态不是“已取消”。
- 装货方式为“冠通”。
- `containerDate` 已填写。

对符合条件的记录：

- `poolStatus` 设置为 `sent_to_inventory`，使其离开采购池并进入采购 / 在途库存。
- 业务 `status` 设置为 `in_transit`，页面显示“海运在途”。
- 保留管理员填写的冠通装柜日期、数量、箱规、金额、CBM、备注和其他采购字段。
- 不创建物流批次，不设置虚假的物流审核信息。
- 从对应采购池的内嵌记录列表中移除。

未填写日期的冠通记录继续留在采购池。若没有可发送记录，显示提示并不执行保存。

### 6. 物流批次只包含整柜

生成或刷新物流批次时，只允许装货方式不是“冠通”的记录进入批次。防护应放在物流批次构建逻辑中，而不只依赖按钮调用方，以确保其他入口也不会误发冠通。

如果当前池没有可分配的整柜记录，显示明确提示。

## 权限

- 统一本池装柜日期：沿用当前管理员权限。
- 修改装货方式：沿用当前管理员权限。
- 发送冠通到在途库存：仅管理员或当前采购池页面已有的管理员角色判断可操作。
- 物流商账号不能看到或处理冠通记录。

## 数据与兼容性

- 不修改 Supabase 表结构。
- 使用现有 `loadingType`、`containerDate`、`status` 和 `poolStatus` 字段。
- 空装货方式继续按整柜兼容旧记录。
- 不自动改写已经进入在途库存的历史记录。
- 已存在于采购池且错误继承整柜日期的冠通记录不会在页面加载时自动清空，避免破坏用户可能已确认的日期；管理员可逐行调整。之后新提交的冠通默认无日期。

### 采购池快照与主表状态一致性

采购池内嵌记录是业务快照，`purchase_records` 是采购记录主表。物流和日期操作不能把旧快照中的 `pending_purchase` 状态写回主表。

- 仍存在于有效采购池中的记录，在采购池页面一律规范为 `submitted_to_pool`。
- 页面加载时，若主表记录为 `pending_purchase`，但相同 ID 仍存在于采购池，则自动修复为 `submitted_to_pool`。
- 采购池逐行编辑、统一日期及其他保存操作必须保留这一规范状态。
- 点击“退回采购人”时，仅点击记录改为 `pending_purchase`；其余池内记录明确保存为 `submitted_to_pool`。
- 不在采购池中的其他待采购记录不得被自动修复或修改。

## 错误处理

- 保存采购池或采购记录任一环节失败时显示错误，并重新加载云端数据，避免前端显示成功但云端未完整保存。
- 批量发送成功后提示发送数量，并保留未填日期冠通的数量提示。
- 不对未填写日期的冠通记录进行部分字段更新。

## 验证

自动测试至少覆盖：

1. 统一本池日期只更新整柜，冠通日期保持不变。
2. 空装货方式按整柜参与统一日期。
3. 已逐行改为其他日期的整柜记录不会被统一日期覆盖。
4. 整柜改冠通时清空日期，冠通改整柜时不自动填日期。
5. 冠通已填日期时批量进入在途库存。
6. 冠通未填日期时继续留在采购池。
7. 整柜不会被冠通直接发送操作处理。
8. 物流批次构建排除冠通。
9. 退回采购人仍只处理单条记录。
10. 采购池旧快照为待采购时，加载和保存会修复为采购池中。
11. 退回一个 SKU 时，同一采购人的其他池内 SKU 保持采购池中。
12. TypeScript 生产构建通过。
