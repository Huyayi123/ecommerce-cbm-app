# 退货原销售 Total Fees 匹配与回退设计

## 目标

修复退货原销售漏查造成的笼统异常提示，并在原订单超过平台可查询期限或 API 未返回时，使用同店铺同 SKU 的最近已结算销售费用回退，保证退货损失可计算且来源可追溯。

## 匹配顺序

每笔退货按以下顺序寻找 Total Fees：

1. 在月报已加载销售中精确匹配 `店铺 + order_id + SKU`。
2. 精确组合不存在时，通过销售 API 使用退货的 `order_id` 查询完整原订单，再匹配相同 SKU。
3. 原订单查询仍无有效记录时，在已加载销售中寻找同店铺同 SKU 最近的有效费用记录。
4. 当前已加载销售没有可用回退记录时，加载数据截止日往前 180 天的销售并寻找同店铺同 SKU 最近记录。

原实现只按 `order_id` 判断订单是否已经加载，真正计算却按 `order_id + SKU` 匹配。新实现统一使用组合键，避免多 SKU 订单中的其他商品阻止原订单查询。

## 有效费用记录

- Sale Status 不能包含 cancel、return 或 refund。
- 数量必须大于 0。
- Total Fees 必须大于 0。
- 优先选择数量为 1 的最新记录，直接使用 Total Fees 作为单件费用。
- 没有单件记录时，选择最新有效记录，并使用 `Total Fees ÷ 数量` 作为单件费用。
- 回退 Total Fees 等于单件费用乘退货数量。

## 成本计算

采购成本、海运费、国内运费和送仓费始终使用当前店铺 SKU 资料库，不依赖原销售订单。

```text
退货基础损失
= 退货数量 ×（采购成本 ZAR + 海运费 + 国内运费 + 送仓费）
+ 退货数量 × 匹配到的单件 Total Fees
```

## 异常与替代标记

- 精确原订单匹配成功：正常计算，不显示替代提示。
- 使用同 SKU 最近订单：显示“原订单超过 180 天或平台未返回，Total Fees 使用同 SKU 最近订单替代”。
- 退货逐笔明细增加“Total Fees 来源订单号”。
- 使用替代费用时该笔可以计算，但月报状态为“不完整/含替代数据”。
- 原订单和同 SKU 回退记录都不存在时，只计算 SKU 资料库中的采购与物流成本，Total Fees 显示 `-`，提示“未找到可用 Total Fees”，月报状态为“不完整”。
- 不再使用“无法匹配已结算的原销售记录”这一笼统提示。

## 数据获取与性能

- 原订单查询按唯一 order_id 去重，受控并发为 5。
- 只有确实需要同 SKU 回退且当前数据没有可用记录时，才加载一次 180 天销售数据。
- 180 天数据使用既有 continuation token 分页，不重复为每个 SKU 拉取。
- 180 天起始日按月报数据截止日向前推 179 天，构成含首尾日期的 180 天范围。

## 页面与 Excel

- 退货逐笔明细显示 Total Fees 来源订单号和替代提示。
- 分摊 Total Fees 显示最终实际代入退货公式的金额。
- Excel 的“退货逐笔明细”增加相同字段。
- SKU 汇总异常原因使用具体的替代或缺失说明。

## 验收标准

- 多 SKU 原订单不会因只检查 order_id 而漏查退货 SKU。
- 可查询的原订单始终优先于同 SKU 回退记录。
- 数量为 1 的同 SKU 已结算记录优先于多件记录。
- 多件回退记录正确使用 Total Fees 除以数量后再乘退货数量。
- 替代记录仅限同一店铺和同一 SKU。
- 替代成功后退货基础损失可计算，且页面明确显示来源订单和替代提示。
- 无任何费用记录时仍扣采购与物流成本，不将整笔退货损失置零。
- 180 天分页只在需要时执行一次。
- TypeScript/Vite 构建通过，取消订单过滤、销售逐笔明细和正数退货损失方向不受影响。
